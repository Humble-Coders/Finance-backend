# [M1] Create the database schema and first migrations

## 📖 Story / Why

Every other ticket in the project is blocked on this one. FinAI stores people's real financial records — transactions, balances, debts — so the schema has to get a handful of things right from the start, because changing them later means migrating live financial data.

Four constraints are locked in the PRD and are not negotiable here:

- **UUID primary keys** — no auto-increment sequences. A second region would mean a second database, and sequential ids collide across them (PRD §4.2).
- **Household-scoped ownership** — every financial record belongs to a `household`, not a `user`. v1 households have exactly one member, but the Family Plan is certain, and retrofitting households onto a user-scoped schema means migrating every table (PRD §4.4).
- **Money as integer minor units** — `amount_minor_units` (BIGINT) plus a `currency` column. Never float, never numeric-with-unclear-scale. The API converts to decimal strings; the database never sees them (PRD §4.4).
- **Source-agnostic transactions** — a `source` discriminator plus reserved external-id fields, so bank-linking (Plaid/Flinks) plugs in later without a schema change (PRD §4.4).

This is also the **first real Alembic migration to run through the Supabase transaction pooler**. `alembic/env.py` was configured for it (`prepared_statement_name_func`) but that path has never been exercised. Expect to validate it here rather than mid-way through a larger feature.

## 🧭 Context

- Repo: `Finance-backend`. Stack: FastAPI + SQLAlchemy 2 (async) + Alembic + Supabase Postgres.
- `app/db.py` already defines `Base` and an engine configured for the pooler. `alembic/env.py` is wired to `Settings.database_dsn`. **No migrations exist yet** — `alembic/versions/` is empty.
- The `vector` and `pgmq` extensions are already enabled on the Supabase project, and the `documents` storage bucket exists.
- The `extraction_jobs` queue was created by hand in the SQL editor. It must also exist as a **guarded migration** so any future environment gets it automatically.

⚠️ **There is no staging environment.** Migrations run against production. There are no real users yet, so the risk is currently low — but:
- Always run `alembic upgrade head --sql` first and read the SQL before applying.
- Every migration must have a working `downgrade()`.
- Do not run destructive operations without checking with the manager.
- Standing up staging is planned but not scheduled; flag it if this becomes uncomfortable.

## 🔑 Access & prerequisites

- Write access to `Humble-Coders/Finance-backend`.
- The `DATABASE_URL` for the Supabase project — **transaction pooler string, port 6543**. Get it from the manager via secure channel or the Render `finai-shared` environment group. Never commit it.
- Supabase dashboard access (to inspect applied migrations) — ask the manager.

## ✅ Scope / What to build

- [ ] SQLAlchemy models for the **full core entity set** (PRD §4.4), even where the feature ships later:
      `household`, `user`, `account`, `document_upload`, `transaction`, `category`, `category_correction`,
      `budget`, `budget_line`, `goal`, `debt`, `health_score_snapshot`, `chat_conversation`,
      `subscription_entitlement`, `country_pack`, `feature_availability`, `disclaimer_version`.
- [ ] **UUID primary keys** on every table (`uuid4` defaults, not database sequences).
- [ ] **Household scoping**: every financial record carries `household_id` with a foreign key and an index.
- [ ] **Money columns** stored as `amount_minor_units BIGINT` + `currency CHAR(3)`, always as a pair. Negative values must be permitted (refunds, debts, overruns).
- [ ] **`household.country_code` is NULLABLE** — every signup route ends with a verified phone, but there is
      a short window between account creation and phone verification where the region is not yet known
      (PRD §4.6).
- [ ] **Auth identity support**: a `user_identity` table (or equivalent) mapping
      `(provider, provider_user_id)` → `user`, so one person's Google, Apple and phone-OTP sign-ins resolve
      to a **single** user and household. Required by ticket 1.2.
- [ ] **`user.phone` is UNIQUE (where non-null)** — the verified phone number is the canonical identity key
      that prevents duplicate accounts across providers (PRD §4.6). Apple's Hide My Email means the email
      address cannot serve this purpose.
- [ ] **Source-agnostic transactions**: `source` enum (`upload` | `manual` | `aggregator`), plus nullable
      `external_id` and `external_account_id` reserved for aggregator integration.
- [ ] **Dedup constraint** on transactions — a unique index over
      `(account_id, occurred_on, amount_minor_units, normalized_description)` so re-importing an overlapping
      statement cannot double-count. Enforced by the database, not application logic.
- [ ] Alembic migration generating all of the above, with a working `downgrade()`.
- [ ] **Guarded migration creating the `extraction_jobs` pgmq queue** — must be a no-op if it already exists
      (it does, in production).
- [ ] **Row Level Security enabled on every table** with no permissive policies. Only the backend's
      `service_role` connection touches these tables; RLS is defence in depth (PRD §4.2).
- [ ] **Seed data migration**: the system category taxonomy (groceries, rent, dining, transport,
      subscriptions, …) and the **CA country pack** (currency `CAD`, locale `en-CA`,
      tax accounts `RRSP`/`TFSA`/`FHSA`).
- [ ] Tests for the models and constraints — in particular, prove the dedup constraint actually rejects a duplicate.

## 🎯 Acceptance Criteria

- [ ] `alembic upgrade head` applies cleanly against the Supabase project **through the transaction pooler**, with no prepared-statement errors.
- [ ] `alembic downgrade base` then `upgrade head` round-trips without error.
- [ ] `alembic upgrade head --sql` produces reviewable SQL (offline mode works).
- [ ] Every table has a UUID primary key; no sequences exist in the schema.
- [ ] Every financial table has `household_id` with a foreign key and an index.
- [ ] Every money column is `BIGINT` minor units paired with a currency column. A grep for `FLOAT`, `REAL`, or `DOUBLE` in the migration returns nothing.
- [ ] Inserting the same transaction twice raises a database integrity error.
- [ ] `household.country_code` accepts NULL.
- [ ] Two identity rows with different providers can point at the same `user`; a second row with the same `(provider, provider_user_id)` is rejected.
- [ ] Inserting a second user with an already-used phone number raises a database integrity error.
- [ ] RLS is enabled on every table (verify in the Supabase dashboard or via `pg_tables`).
- [ ] Re-running the queue migration on a database where `extraction_jobs` already exists succeeds without error.
- [ ] Seeded system categories and the CA country pack are present after migration.
- [ ] `pytest` passes; CI green.

## 🚫 Out of scope

- API endpoints over these tables (later M1 tickets and M2+).
- The capabilities resolver reading country packs — ticket **1.3**.
- Any business logic, budget generation, or scoring.
- Phase 2/3 tables not listed above (bank-link credentials, split expenses, investments holdings).
- Standing up a staging environment.
