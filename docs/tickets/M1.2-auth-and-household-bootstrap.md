# [M1] Wire authentication and bootstrap the household

## 📖 Story / Why

Users sign in through Supabase Auth; this API never issues credentials of its own. It only needs to **verify** the token it is handed and turn it into a known user with a household.

Signup will offer three routes (M2 builds the UI):

1. **Phone + country code with SMS OTP** — the primary path
2. **Google sign-in**
3. **Apple sign-in**

**Phone collection is lazy** — a Google or Apple user is never blocked on providing one (PRD §4.6). Region for those users comes from **device signals plus a one-tap confirmation** instead. So this ticket must handle a freshly authenticated user who has **no phone number at all**, possibly forever: the household is still created, and `country_code` stays NULL until the confirmation step in M2 sets it.

Everything downstream — every household-scoped query, entitlements, region gating — depends on this mapping existing and being correct.

## 🧭 Context

- Repo: `Finance-backend`.
- `app/auth.py` already verifies Supabase JWTs against the project's JWKS (with an HS256 fallback) and returns an `AuthenticatedUser` with `user_id`, `email`, `phone` and raw claims. **That part works and needs no rewrite.**
- What does not exist: any link between a verified token and rows in our `user` / `household` tables.
- All three providers issue **Supabase-issued JWTs**, so verification is identical for each. The difference is only which claims are populated — Google/Apple tokens will have `email` but no `phone`.
- Only the backend touches the database (`service_role`); clients never do (PRD §4.2).

## 🔑 Access & prerequisites

## ✅ Scope / What to build

- [ ] `GET /me` — verifies the caller's JWT and returns their user + household.
- [ ] **Idempotent household bootstrap**: on the first authenticated call for an unknown `sub`, create a
      `user` row and a **single-member `household`**, and link them. Calling `/me` repeatedly must never
      create a second household.
- [ ] Persist from the token's claims what is present: `email`, `phone`, provider. **Tolerate a permanently
      missing phone** — phone collection is lazy, so a Google/Apple user may never have one.
- [ ] **Persist Apple's `email` and name on the very first authorization.** Apple returns them only once;
      every later sign-in omits them, and they are lost permanently if not stored then. A Hide My Email
      relay address (`…@privaterelay.appleid.com`) is valid and deliverable — never treat it as fake.
- [ ] **Identity collision handling** (PRD §4.6): when a new sign-in's **verified email matches an existing
      user**, link the identity to that existing user and household rather than creating a second one.
      When it does not match — as with Apple's private relay — return a response the client can use to
      prompt *"this email already has an account"*. **Never silently create a second account:** two
      households means split financial data that support cannot repair.
- [ ] **Accept device signals** on the bootstrap call — timezone, OS region, and (Android) SIM country —
      and store them on the household for M2's region inference to consume. This ticket **stores** them;
      resolving a region from them is ticket 2.1.
- [ ] `household.country_code` is left **NULL** when no phone is available. Do **not** guess a region.
- [ ] A reusable FastAPI dependency (e.g. `current_household`) that resolves the caller to their household
      row, for every later endpoint to depend on.
- [ ] Return 401 with a clear body for missing, malformed, or expired tokens.
- [ ] Handle the race where two concurrent first requests arrive for the same new user — exactly one
      household must result (unique constraint plus insert-conflict handling, not a check-then-insert).
- [ ] Tests: new user creates one household; repeated calls are idempotent; missing phone is tolerated;
      concurrent bootstrap produces one household; invalid/expired tokens are rejected; a matching verified
      email links to the existing household instead of creating a second; device signals round-trip.

## 🎯 Acceptance Criteria

- [ ] `GET /me` with a valid Supabase JWT returns the user and their household.
- [ ] A brand-new user gets exactly one household on first call; a second call returns the same one.
- [ ] Two concurrent first requests for the same new user still produce exactly one household (covered by a test).
- [ ] A token with no `phone` claim succeeds, and the household's `country_code` is NULL.
- [ ] Signing in with a provider whose verified email matches an existing user links to that household — a second household is **not** created (covered by a test).
- [ ] Apple's first-authorization email and name are persisted; a later sign-in without them does not overwrite the stored values with nulls.
- [ ] Device signals sent on the bootstrap call are stored and readable back.
- [ ] Missing / malformed / expired tokens all return 401, never 500.
- [ ] The `current_household` dependency is used by `/me` and is documented for reuse.
- [ ] No endpoint added here reads or writes another household's data.
- [ ] `pytest` passes; CI green.
