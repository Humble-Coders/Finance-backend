# [M1] Back /capabilities with the database

## 📖 Story / Why

Both mobile clients render their entire UI from one payload: what region the user is in, what currency to show, and which features are on. **There are no per-country branches in client code** — if the payload doesn't say a feature is enabled, the client doesn't show it (PRD §4.6).

`app/api/capabilities.py` currently returns that payload from a hardcoded resolver. The shape is right; the data is fake. This ticket makes it real.

The rule that matters most: **the payload controls what is *shown*; the API independently enforces what is *allowed*.** A hidden feature is not a secured feature. This ticket builds the resolver every gated endpoint will later call.

## 🧭 Context

- Repo: `Finance-backend`. Existing stub: `app/api/capabilities.py` — keep the response shape, replace the source of the data.
- Ticket 1.1 creates `country_pack`, `feature_availability`, `disclaimer_version` and `subscription_entitlement`, and seeds the CA country pack.
- **`household.country_code` can be NULL** — Google/Apple users have no phone, and therefore no region, until the M2 follow-up step. The resolver must handle this without failing and without guessing.
- v1 launches Canada-only, but **signup is never hard-blocked on region** (PRD §4.6). Features are gated; account creation is not.

## ✅ Scope / What to build

- [ ] **One resolver**: `resolve(plan, region, rollout_flags, user_overrides)` reading `country_pack`,
      `feature_availability` and `subscription_entitlement` from the database. Plan entitlements, region
      gating and rollout flags **compose here** — they must not become three parallel systems.
- [ ] `GET /capabilities` returns the resolved payload for the authenticated caller's household.
- [ ] **Unknown-region fallback**: when `country_code` is NULL, return a safe default (region `null`,
      currency and locale from a documented default) with region-dependent features disabled and a
      `reason` explaining why. Never guess a country, never 500.
- [ ] An **enforcement helper** — e.g. `require_feature("bank_linking")` — that any endpoint can depend on
      to return 403 when a feature is off for that household. Used by at least one endpoint (or covered by a
      test) to prove the pattern.
- [ ] Country-specific content (tax account names, disclaimer version) comes from the country pack, never
      from Python constants.
- [ ] Tests: CA household gets the CA pack; NULL-region household gets the documented fallback; a
      plan-gated feature is off on free and on for paid; `require_feature` returns 403 when disabled.

## 🎯 Acceptance Criteria

- [ ] `GET /capabilities` returns live database-backed values for a CA household — currency `CAD`, locale `en-CA`, tax accounts `RRSP`/`TFSA`/`FHSA`.
- [ ] A household with `country_code` NULL gets a successful response with the documented fallback and disabled region-dependent features, each carrying a `reason`.
- [ ] Adding a new country requires **inserting rows only** — no code change and no deploy. Demonstrated by a test that inserts a second country pack and resolves against it.
- [ ] `require_feature` returns 403 for a disabled feature and passes through when enabled.
- [ ] There is exactly one resolver function; grep shows no second place composing plan and region.
- [ ] No `if country == "CA"`-style branch anywhere in the codebase.
- [ ] `pytest` passes; CI green.

## 🚫 Out of scope

- Billing, purchases, or changing a household's plan — M7.
- Region resolution from a phone number — **M2 (2.1)**. This ticket only *reads* `country_code`.
- Client-side rendering of the payload — M2 mobile tickets.
- Per-market pricing (OD3 in the PRD is still open).
