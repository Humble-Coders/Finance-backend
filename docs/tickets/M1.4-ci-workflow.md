# [M1] Add a CI workflow

## 📖 Story / Why

The backend's first three deploys to Render all failed, and **every one of them was catchable before merge**:

1. `metadata-generation-failed` — Render used Python 3.14, which has no `pydantic-core` wheels
2. `ModuleNotFoundError: psycopg2` — a config/driver mismatch that surfaced as an import error
3. `ProgrammingError` — prepared-statement names colliding through the pooler

Each cost a deploy cycle and a debugging session. A CI job that installs dependencies on the pinned Python and runs the test suite would have caught the first two on the pull request. As the schema and money logic grow, the value only increases — this is a money app, and the money tests are the ones that matter most.

## 🧭 Context

- Repo: `Finance-backend`. No CI exists today.
- Python is pinned to **3.12.8** in `.python-version` and via `PYTHON_VERSION` in `render.yaml`. **CI must use the same version** — testing on a different interpreter than deploys is how failure #1 happened.
- Dependencies: `requirements.txt` (runtime) and `requirements-dev.txt` (adds `pytest`, `pytest-asyncio`, `ruff`).
- Existing suite: `tests/test_money.py`, `tests/test_dsn.py`. These are pure unit tests — **no database or network required**, which keeps CI fast and secret-free.

## 🔑 Access & prerequisites

- Write access to `Humble-Coders/Finance-backend`.
- **No secrets are needed.** The current tests touch neither the database nor any external service, so the workflow must not require repository secrets. If a future test needs one, that is a separate conversation with the manager.

## ✅ Scope / What to build

- [ ] `.github/workflows/ci.yml`, triggered on pull requests to `main` and on pushes to `main`.
- [ ] Set up **Python 3.12.8**, matching `.python-version` and `render.yaml`.
- [ ] `pip install -r requirements-dev.txt` — this alone reproduces the wheel-availability failure that broke the first deploy.
- [ ] Run `pytest`.
- [ ] Run `ruff check` (lint) and `ruff format --check` (formatting).
- [ ] Cache pip downloads so runs stay fast.
- [ ] Add a `ruff` configuration to `pyproject.toml` (or `ruff.toml`) if none exists, and **fix any existing violations in this ticket** so the first green run is genuinely green.
- [ ] Add a CI status badge to `README.md`.

## 🎯 Acceptance Criteria

- [ ] Opening a pull request runs the workflow automatically.
- [ ] The workflow installs on **Python 3.12.8** — the version is visible in the run log.
- [ ] `pytest` runs and passes; a deliberately broken test makes CI red (verify once, then revert).
- [ ] `ruff check` and `ruff format --check` pass on the current codebase.
- [ ] The workflow needs **no repository secrets** and does not contact the database.
- [ ] A full run completes in under about two minutes.
- [ ] The README badge reflects the real status.

## 🚫 Out of scope

- Spinning up Postgres in CI to test migrations. Worth doing once the schema lands (**suggest as a follow-up ticket**), but not here.
- Deploy automation — Render already auto-deploys from `main`.
- Coverage thresholds, type checking (`mypy`), or security scanning. Reasonable later; each is its own decision.
- CI for the mobile repo — separate ticket, different toolchain.

## 🔗 Dependencies

- **None.** Can be done in parallel with 1.1–1.3, and ideally lands first so those tickets get checked.
