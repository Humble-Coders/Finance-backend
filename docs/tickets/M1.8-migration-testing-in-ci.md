# [M1] Test migrations against a real Postgres in CI

## 📖 Story / Why

There is **no staging environment**, so `alembic upgrade head` runs first against **production** — a database holding people's financial records. Backend CI (#13) deliberately excludes database tests to stay fast and secret-free.

Each decision is defensible alone. Together they mean **production is the first place any migration is ever executed.** That is survivable today because there are no real users; it stops being survivable the moment there are.

This closes the gap cheaply: spin up a throwaway Postgres in CI and prove every migration applies, reverses, and re-applies before it can reach production.

## 🧭 Context

- Repo: `Finance-backend`. Builds on the workflow from **#13**; this adds a job, it does not replace one.
- Ticket **#10** creates the first migrations, including a **guarded** `pgmq` queue migration that must be a no-op when the queue already exists.
- Production uses Supabase's **transaction pooler**, which needed `prepared_statement_name_func` to work at all. A plain Postgres container has no pooler, so **CI proves the migrations are valid — not that they survive the pooler.** Say so in the workflow comments; do not let a green CI create false confidence about that specific risk.
- `pgmq` and `vector` are Postgres **extensions**. The container image must provide them, or the migrations that use them must be skippable — see Scope.

## 🔑 Access & prerequisites

- Write access to `Humble-Coders/Finance-backend`.
- **No secrets.** The database is a throwaway service container; the connection string is local to the runner.
- Ticket **#13 merged** (the workflow to extend), and **#10 merged** (migrations to test).

## ✅ Scope / What to build

- [ ] Add a job to `.github/workflows/ci.yml` running a **Postgres service container** with the `pgmq` and
      `vector` extensions available (a Supabase-flavoured or extension-bearing image, or install them in a
      setup step).
- [ ] Run `alembic upgrade head` against it — proves every migration applies to an empty database.
- [ ] Run `alembic downgrade base`, then `alembic upgrade head` again — proves `downgrade()` works and the
      migrations are re-runnable. **A broken `downgrade()` is only ever discovered when you urgently need it.**
- [ ] Run `alembic upgrade head` **twice** in a row to prove the guarded queue migration is genuinely a no-op
      the second time.
- [ ] Fail the job on any `alembic` warning about **multiple heads** — divergent migration branches are a
      merge-order bug that is painful to untangle later.
- [ ] Comment in the workflow that this validates migration **correctness**, not pooler behaviour.

## 🎯 Acceptance Criteria

- [ ] Opening a pull request runs the migration job automatically.
- [ ] `upgrade head` → `downgrade base` → `upgrade head` completes green.
- [ ] Running `upgrade head` twice is a no-op the second time.
- [ ] A deliberately broken `downgrade()` makes CI red (verify once, then revert).
- [ ] Two divergent migration heads make CI red.
- [ ] The job needs **no repository secrets**.
- [ ] Total CI time stays under about five minutes.

## 🚫 Out of scope

- Reproducing the Supabase transaction pooler in CI — not practical; `/readyz` on the deployed service remains the check for that.
- Standing up a staging environment. **Still worth doing** — this ticket reduces the risk of migrating straight to production, it does not remove it.
- Seeding realistic data or performance testing.
