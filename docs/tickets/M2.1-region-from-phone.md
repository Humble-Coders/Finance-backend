# [M2] Resolve the household's region from the verified phone

## 📖 Story / Why

Every signup route ends with a verified phone number (PRD §4.6): phone OTP directly, Google and Apple through the phone step that immediately follows the provider handshake. That number is already the **identity key** (#11). This ticket makes it the **region key** too.

`household.country_code` decides what a user sees — features, tax-account names, disclaimers, currency (PRD §4.6). Today nothing ever sets it: every household stays `NULL`, so every user gets the "unknown region" payload forever, and `/capabilities` keeps asking for a phone the user has already verified.

Region is resolved **server-side** from the stored number with libphonenumber — never in the client, so there is one implementation and a modified app cannot spoof it. `+1` is the whole North American Numbering Plan (Canada, the US, 20+ Caribbean countries and US territories), so a hand-written area-code list is wrong from day one; libphonenumber keeps that mapping current.

Two launch rules shape everything here (PRD §4.6):
- **Signup is never hard-blocked on region.** Anyone may create an account; features are gated, accounts are not.
- **The region override must be reachable during onboarding**, not only in settings — a misdetected Canadian must be able to fix it before they ever reach support.

## 🧭 Context

- Repo: `Finance-backend`.
- **No brief.** M2 is drafted from `docs/ROADMAP.md` (2.1) and the PRD, which are the yardstick for review (manager decision, 2026-09-11).
- **How the phone arrives today:** `app/auth.py` reads the Supabase JWT's `phone` claim. Real Supabase tokens carry it as **digits with no `+`** (e.g. `14165550100`) — Supabase strips the `+` when it stores a number — while the existing test fixtures use `+1416…`. Identity linking is unaffected (every stored phone comes from the same claim), but the parser below must accept **both** forms, and at least one test must use the real, `+`-less form. `resolve_user` / `_absorb_claims` in `app/services/identity.py` store it on `user.phone` and audit changes in `user_phone_change`. A Google/Apple user's token gains a `phone` claim once they verify one (2.3 does that on the client) — the backend already absorbs it. **Nothing needs to change in how phones are captured.**
- **What is missing:** anything that turns `user.phone` into `household.country_code`. `_create` sets it to `NULL` deliberately and nothing updates it (`app/services/identity.py`, `Household` in `app/models/identity.py`).
- **Two endpoints disagree today** (seen live in Humble-Coders/FinAI-Mobile-2026#6): `/me` builds `onboarding_required` from `user.phone` (`app/api/me.py:24`), `/capabilities` from `household.country_code` (`app/services/capabilities.py:208-209`). A user with a verified phone is "done" by one and "needs phone" by the other. After this ticket they read **one** function.
- The capabilities resolver already handles any region: a launched pack (CA) returns its content; an unlaunched or unknown country keeps its own currency/locale and gets no content (#19/#20). No resolver change is needed.
- The CA country pack points at `disclaimer_version: "ca-v1"`, but **no `disclaimer_version` row exists** (`app/models/platform.py:160`). Once regions resolve, Canadian users start receiving that pointer.
- No phone-number library is installed yet.
- **Migrations reach production.** There is no staging database; the only database is production. Rehearse migrations locally with the Docker Postgres from #15 (`scripts/check_migrations.sh`) and let CI's `database` job prove them. **Never run `alembic upgrade` against production before the PR is approved.**

- **No region-confirmation screen** (manager decision, 2026-09-11). The 2026-08-29 decision (PRD §9) removed device-signal inference and the `needs_region_confirmation` state; PRD §4.6 steps 2–4 predate it. Region is libphonenumber's answer, shown during onboarding with an option to change it (2.3). A number libphonenumber cannot place gets an explicit `region` onboarding step instead of a guess.

- **Signup consent is in scope** (manager decision, 2026-09-11). PRD Appendix A.5, item 1 requires an express, versioned, audit-logged consent to the account terms at signup; it is not on the roadmap row, so it is added here (API) and in 2.3 (screen). ## ✅ Scope / What to build

- [ ] Add **`phonenumbers`** (the Python port of Google's libphonenumber), pinned, to `requirements.txt`.
- [ ] **`region_for_phone(phone: str) -> str | None`** in `app/services/region.py` — pure, no I/O:
      normalise to E.164 (add the `+` when it is missing, accept it when present), parse, and return the ISO 3166-1 alpha-2 region from
      `region_code_for_number`. Return `None` — never a guess — for anything unparseable, invalid, or that
      libphonenumber cannot place.
- [ ] **Derive the region when a phone first appears.** When the caller's household has `country_code` NULL
      and the user now has a phone, set `country_code = region_for_phone(user.phone)` in the same
      transaction as identity resolution. **Never overwrite an existing region automatically** — a later
      phone change must not silently move someone's region (and currency); that is what the override is for.
- [ ] **Audit every region change.** New table `household_region_change` (household-scoped): `previous`,
      `new`, `source` (`phone` | `user`), the acting `user_id`, timestamp. The first derivation is logged with
      `source = phone` (PRD §4.6: region changes are audit-logged).
- [ ] **Region override:** `PUT /me/region` with `{"country_code": "CA"}` — any valid ISO alpha-2 code, not
      only launched ones (signup is never blocked on region). Validate against the ISO list; audit with
      `source = user`; return the updated `/me` payload. Rejected codes → 422.
- [ ] **One onboarding rule, used by both endpoints.** A single function returns the outstanding steps:
      `["phone"]` while there is no phone; `["region"]` while there is a phone but no region (a number
      libphonenumber could not place); `[]` otherwise. `/me` and `/capabilities` both call it.
- [ ] **Signup consent:** table `consent_event` (user, `kind` = `account_terms`, `policy_version`,
      timestamp, append-only); `POST /me/consent` records it; `/me` reports whether the current terms version
      is accepted, and `onboarding_required` includes `"consent"` until it is.
- [ ] **Seed `disclaimer_version`** for `(CA, ca-v1)` and the first account-terms policy version,
      with body text clearly marked as a **draft pending counsel review** (PRD §8 Q13). Real copy replaces it
      before launch (roadmap → Before launch).
- [ ] Tests (see Acceptance Criteria).

## 🎯 Acceptance Criteria

- [ ] `region_for_phone` is covered by a table-driven test: `+1 416…` → `CA`, `+1 212…` → `US`, `+1 876…` → `JM`, `+1 787…` → `PR`, `+44…` → `GB`, `+91…` → `IN`, `+61…` → `AU`, garbage/empty → `None`, and the Supabase test number `14165550100` (fictional 555-01xx) — **whatever libphonenumber returns is recorded in the test**, so test signups' behaviour is known rather than assumed.
- [ ] A new phone-OTP user's household gets `country_code` from their number on the first authenticated call; a Google/Apple user's household gets it on the first call after their phone is verified.
- [ ] An existing region is **not** changed by a later phone change (covered by a test).
- [ ] `PUT /me/region` changes the region, writes an audit row with `source = user`, and rejects a non-ISO code with 422.
- [ ] Every region change — derived or overridden — has a `household_region_change` row.
- [ ] `/me` and `/capabilities` return the **same** `onboarding_required` for the same caller in every state: no phone, phone without region, complete (covered by a test that calls both).
- [ ] A number libphonenumber cannot place leaves `country_code` NULL and reports `onboarding_required: ["region"]`; the override then completes onboarding.
- [ ] Consent is recorded with its policy version, is append-only, and `onboarding_required` includes `"consent"` until the current version is accepted.
- [ ] A `disclaimer_version` row backs `ca-v1`.
- [ ] Migrations apply, reverse and re-apply cleanly in CI's `database` job; `pytest` passes; CI green.
- [ ] No endpoint reads or writes another household's data.
