# [M2] Persist the financial setup wizard

## 📖 Story / Why

Right after signup, users get a short, **skippable** wizard: monthly after-tax income, existing debts and loans, current investments (amounts only in v1), and basic monthly obligations (PRD F1). Its answers **seed the first dashboard** (M4) — the budget generator and health score start from them before a single statement is uploaded.

This ticket gives the wizard somewhere to save. It is small but load-bearing: these are money figures, so they follow the money rules exactly (integer minor units in Postgres, decimal strings on the wire — PRD §4.4), and they must never leak between households.

## 🧭 Context

- Repo: `Finance-backend`.
- **No brief.** M2 is drafted from `docs/ROADMAP.md` (2.2) and the PRD, which are the yardstick for review (manager decision, 2026-09-11).
- **Reuse `debt`** (`app/models/planning.py`): name, balance, minimum payment, interest rate in basis points, currency — exactly what the wizard asks. Debts entered here have no `account_id`.
- **Nothing stores income, investments or obligations yet.** `account` (kind `investment`) is statement-backed with no balance column, so it is not the place for a typed-in amount.
- Money conversion already exists: `app/core/money.py` (decimal string ↔ integer minor units). **Use it; do not write another.**
- Every table is household-scoped (`HouseholdScopedMixin`); every endpoint depends on `current_household`.
- The household's currency comes from the capabilities resolver (the country pack's currency; the documented default when the region is unknown). v1 is CAD-only in practice.
- **Migrations reach production** — same rule as 2.1: rehearse with Docker/CI, never run against production before approval.

- **Data model** (manager-confirmed, 2026-09-11): one `financial_profile` row per household for income and wizard status; new `obligation` and `investment` tables; debts in the existing `debt` table, marked as entered through setup.

## ✅ Scope / What to build

- [ ] **Migration:**
      - `financial_profile` — one per household (unique `household_id`): `monthly_income_minor_units`
        (nullable — skipping a step is allowed), `currency`, `setup_completed_at`, `setup_skipped_at`.
      - `obligation` — household-scoped: `name`, `monthly_amount_minor_units`, `currency`.
      - `investment` — household-scoped: `name`, `amount_minor_units`, `currency`.
      - `debt.entered_via_setup` (boolean, default false) — so the wizard can replace *its* debts without
        touching debts that arrive later from statements.
- [ ] **`GET /financial-setup`** → `{status, income, debts, investments, obligations}`, where `status` is
      `not_started` | `skipped` | `completed`, and every amount is a **decimal string**.
- [ ] **`PUT /financial-setup`** — replaces the wizard-owned data in one transaction. Idempotent, so the client
      may call it after **every step** (making the wizard resumable) and again at the end with
      `"finished": true`, which sets `setup_completed_at`.
- [ ] **`POST /financial-setup/skip`** — sets `setup_skipped_at`; keeps anything already saved.
- [ ] **Validation → 422 with a field path:** amounts are non-negative decimal strings with at most the
      currency's minor-unit digits; interest rate is an optional percentage string converted to basis points;
      names 1–255 characters; at most 20 items per list.
- [ ] **Onboarding must be complete first:** while `onboarding_required` is non-empty (2.1), these endpoints
      return 409 with `onboarding_required`, since the currency is not known yet.
- [ ] Tests (see Acceptance Criteria).

## 🎯 Acceptance Criteria

- [ ] Amounts round-trip exactly: `"1200"` is stored as `120000` minor units and returned as `"1200.00"`; no float appears anywhere in the path.
- [ ] Negative amounts, extra decimal places, non-numeric strings and oversized lists return 422 naming the field.
- [ ] Two identical `PUT`s leave identical data (idempotent), and a `PUT` with fewer debts removes the dropped ones.
- [ ] A `PUT` never touches a debt with `entered_via_setup = false` (covered by a test).
- [ ] `status` moves `not_started` → `completed` with `finished: true`, and `not_started` → `skipped` with skip; data saved before a skip is kept.
- [ ] Before onboarding is complete, all three endpoints return 409 with `onboarding_required`.
- [ ] A household can never read or write another household's setup (covered by a test).
- [ ] Migrations apply, reverse and re-apply cleanly in CI's `database` job; `pytest` passes; CI green.

## ⚠️ Superseded in part by 2.5

A later manager decision (2026-09-12, PRD §9) makes part of this wizard **mandatory**: phone, region, monthly income and monthly expense are required to reach the app, while debts, investments and itemised obligations stay optional and editable later from the profile.

What that changes, in **2.5**, not here:

- **`monthly_expense_minor_units`** joins `financial_profile`; this ticket stores income only.
- **The gate moves into the onboarding rule.** `onboarding_required` gains `financial_setup` while the mandatory figures are missing, enforced server-side — so the mandatory half needs no wizard status at all.
- **Skip and status become the optional half's business.** `POST /financial-setup/skip` and the `not_started` / `skipped` / `completed` statuses in this ticket describe a wholly skippable wizard; 2.5 revisits them, including whether a save should clear an earlier skip.

Everything this ticket builds stands: the tables, the replace-in-one-transaction save, the money boundary and the ordering. Read the status semantics below as 2.5's starting point, not the final contract.
