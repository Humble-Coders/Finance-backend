# [M2] Make the core financial setup mandatory

## 📖 Story / Why

A dashboard with no income and no expense figure can say nothing useful: no budget, no health score, nothing but empty cards. So the first session would open onto a product with nothing in it.

A manager decision (2026-09-12, PRD §9) therefore splits the setup wizard in two:

- **Mandatory to reach the app:** a verified **phone**, a resolved **region** (both already enforced by 2.1), **monthly after-tax income**, and **monthly expense**.
- **Optional, editable later from the profile:** debts and loans, investments, and the itemised breakdown of monthly obligations.

This supersedes the wholly **skippable** wizard described in PRD F1 and built by 2.2 (#25). Two figures is a deliberate bar: enough for the dashboard to say something, few enough to keep the ~30-second target honest.

**The gate is enforced server-side.** A client-side check is not a gate — anyone with a token can call the API directly (PRD §4.6, backend `CLAUDE.md`).

## 🧭 Context

- Repos: **`Finance-backend`** (the field, the rule, enforcement) and **`FinAI-Mobile-2026`** (routing).
- **No brief.** M2 is drafted from `docs/ROADMAP.md` (2.5) and the PRD, which are the yardstick for review.
- **What exists after #24 and #25:**
  - one onboarding rule (`app/services/onboarding.py`) returning ordered steps — `phone`, `region`, `consent` — read by both `/me` and `/capabilities`; the apps route on it and never infer a step themselves;
  - `financial_profile` with `monthly_income_minor_units`, `currency`, `setup_completed_at`, `setup_skipped_at`; `obligation`, `investment`, and wizard-owned rows in `debt`;
  - `GET`/`PUT`/`POST /financial-setup(/skip)`, which currently refuse with 409 until onboarding is complete.
- **The circularity to avoid:** the wizard endpoints refuse while `onboarding_required` is non-empty, so adding `financial_setup` to that list without care would lock the user out of the very endpoint that clears it. The gate must let the wizard through while blocking everything else.
- **Mobile:** `OnboardingStep` decodes unknown values to `UNKNOWN` and treats them as incomplete (#6), so an old build meets the new step safely — it simply cannot clear it.
- **Migrations reach production.** Rehearse against the local Docker Postgres and CI; never run against production before approval.

## ✅ Scope / What to build

**Backend**
- [ ] **`financial_profile.monthly_expense_minor_units`** (nullable, same money rules as income) and a migration for it.
- [ ] **`monthly_expense` in the wizard payload** — `GET` returns it, `PUT` accepts it, validated exactly as income is (non-negative decimal string, currency precision, named field on failure).
- [ ] **`financial_setup` joins the onboarding rule** (`app/services/onboarding.py`), after `consent`, while **either** mandatory figure is missing. `/me` and `/capabilities` both report it, as one rule.
- [ ] **The wizard endpoints stay reachable** while `financial_setup` is outstanding: they must refuse only for the *other* steps (no phone, no region, no consent), or the user can never clear it. Covered by a test.
- [ ] **Gated endpoints refuse while it is outstanding** — a reusable dependency (`require_onboarded`, or extending `require_feature`'s pattern) that any later endpoint can depend on. Nothing in M2 needs gating yet, so prove it on a throwaway route as `require_feature` did.
- [x] **No status at all** — decided during the build (manager decision, 2026-09-12; PRD §9). With the mandatory figures enforced by the rule, the optional half needs no state: a skipped answer and an unasked one are stored identically, as no row, so absence is the record. This removes the `status` field, `POST /financial-setup/skip`, the `finished` flag and the `setup_completed_at` / `setup_skipped_at` columns behind them. It also answers #28's open question — there is no skip left to clear, and a single whole-wizard timestamp could never have named *which* optional field was declined.

**Mobile** — the shared contract only (manager decision during the build).

- [ ] **`OnboardingStep.FINANCIAL_SETUP`**, plus `REGION` and `CONSENT`: the API has sent those two since #24 and they were still decoding to `UNKNOWN`, leaving the app unable to route to half the steps.
- [ ] Decoding tests for every step the API can send, and for an unknown one still counting as incomplete.
- [ ] **Routing and the screens belong to 2.3 (#16) and 2.4 (#17)**, not here: this repo has no navigation layer and no wizard to attach them to, and both tickets already carry the no-Skip requirement. The wizard's strings land there too, with the design in hand — keys invented here, against screens that do not exist, would only be guesses for 2.4 to redo.

## 🎯 Acceptance Criteria

- [ ] A household missing income or monthly expense reports `onboarding_required` including `financial_setup`, from **both** `/me` and `/capabilities`; supplying both clears it.
- [ ] The wizard endpoints work while `financial_setup` is the only outstanding step, and still refuse when phone, region or consent is missing (covered by a test).
- [ ] A gated endpoint refuses while `financial_setup` is outstanding and passes once it is cleared (throwaway route, as `require_feature`).
- [ ] `monthly_expense` round-trips exactly (`"1800"` → `180000` → `"1800.00"`), and a bad value is refused naming the field.
- [ ] *(deferred to 2.4 — no wizard exists yet)* The apps cannot reach home while `financial_setup` is outstanding, on Android and iOS.
- [ ] *(deferred to 2.4)* The mandatory screens offer no Skip; the optional ones do, and the optional fields can be edited afterwards.
- [ ] An old mobile build (unknown step) does not crash and does not silently pass the gate.
- [ ] Migrations apply, reverse and re-apply cleanly in CI; `pytest` passes; CI green on both repos.

## 🚫 Out of scope

- Per-step "declined" flags — distinguishing "skipped this question" from "not answered yet" is its own feature.
- The profile/settings screens where optional data is edited later — a separate ticket.
- Using the figures (budget, health score) — M4.
