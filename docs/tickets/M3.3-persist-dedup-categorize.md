# [M3] Save extracted transactions: accounts, dedup and categories

## 📖 Story / Why

3.1 turns a statement into rows and hands them back. Nothing keeps them. This ticket is
where an import becomes data the rest of the product can use — and where the two rules
that decide whether that data is trustworthy live: **a transaction must never be
double-counted**, and **every transaction needs a category** before a budget or a health
score can mean anything.

Re-importing an overlapping statement is not an edge case, it is what people do: January's
statement and the January–February one share two weeks of rows. If dedup is even slightly
wrong, the product quietly reports spending that never happened, and no one finds out from
a test.

## 🧭 Context

- Repo: `Finance-backend`. No brief — drafted from `docs/ROADMAP.md` and the PRD.
- **Depends on #34 (3.1)**, which creates `statement_import` and returns parsed rows.
- The dedup index already exists from migration 1.1: `uq_transaction_dedup` on
  `(account_id, occurred_on, amount_minor_units, normalized_description)`
  (`app/models/money.py`). **It is the enforcement**, not a hint — application-level dedup
  fails the moment two imports run concurrently.
- `transaction.normalized_description` is **NOT NULL and nothing produces it yet**
  (carry-over from `handoffs/ticket-10.md`). It is part of the dedup key, so if it is not
  deterministic, dedup silently stops working — the same statement imported twice lands
  twice and nothing errors.
- `category` and `category_correction` exist (`app/models/categorization.py`).
  `category.household_id` is NULL for the shared system taxonomy and set for user-defined
  ones, with a partial unique index enforcing one system row per slug. **The taxonomy has
  never been seeded.**
- `account` exists and has **never been written to** — nothing creates one. Manager
  decision, 2026-09-21: the minimum needed to import lands here rather than in a ticket of
  its own.
- Money conversion is `app/core/money.py` only. Never a float, never a second converter.
- Every 409 calls `log_conflict` first (`app/services/conflicts.py`).
- **Migrations reach production.** Rehearse against Docker/CI; never run against production
  before approval.

## ✅ Scope / What to build

- [ ] **Minimal accounts.** `POST /accounts` (`name`, `kind`, `currency`) and
      `GET /accounts`. Household-scoped, name unique per household so "RBC Chequing" cannot
      exist twice — a duplicate account is a silent dedup hole, because the dedup key starts
      with `account_id`. Full account management (rename, archive, balances) stays for M4.
- [ ] **`normalized_description`** in `app/services/` as a pure, documented function:
      lower-case, collapse whitespace, strip punctuation, and strip the noise that makes the
      same merchant look different between statements — trailing reference numbers, store
      numbers, dates embedded in the description, `POS`/`PURCHASE`/`DEBIT` prefixes.
      **Deterministic and versioned:** changing it changes the dedup key for every row ever
      written. So a change to this function **must ship with a backfill migration** that
      recomputes `normalized_description` for every existing transaction from its stored
      `description` — otherwise dedup silently stops working against the whole existing
      corpus, not just against new imports. Put that rule in the docstring, next to the
      version constant, where the next person to "just tidy up the regex" will read it.
- [ ] **`POST /statements/{import_id}/transactions`** — persist the rows the client
      confirms, in one transaction: resolve the account, convert amounts through
      `app/core/money.py`, compute `normalized_description`, set
      `source = TransactionSource.upload` and `statement_import_id`.
- [ ] **Dedup, two layers.** Insert with `ON CONFLICT DO NOTHING` against
      `uq_transaction_dedup` and count what was skipped; then a **fuzzy near-match** check
      on **`(account_id, occurred_on ± 3 days, amount_minor_units)` alone**. Description
      similarity raises confidence in the match; it must **not** be a condition of it. The
      case that makes this matter is re-importing a statement after the parse or the
      normalizer improved: the same purchase now carries a different description, so the
      unique index cannot see it, and a similarity gate would miss it for exactly the
      reason it changed. Near-matches are **flagged for review, never dropped silently**.
      The response says how many were saved, how many were exact duplicates and how many
      look like near-duplicates.
- [ ] **Seed the system category taxonomy** (migration). Proposed list — **edit this before
      building**: `groceries`, `dining`, `transport`, `fuel`, `housing`, `utilities`,
      `phone_internet`, `subscriptions`, `shopping`, `health`, `personal_care`,
      `entertainment`, `travel`, `education`, `childcare`, `insurance`, `debt_payment`,
      `savings_transfer`, `income`, `fees`, `other`. Slugs are stable identifiers; display
      names go through i18n on the client.
- [ ] **Categorization.** For each row, send **only `(merchant_string, amount)`** to the
      model and map the answer onto a category slug. An answer that is not a known slug
      becomes `other` with `needs_review = true` — never a new category invented by a model.
- [ ] **Household corrections feed the prompt.** Existing `category_correction` rows for the
      household are injected as few-shot examples, **for that household only** — never
      pooled across users (PRD §4.5, Appendix A.5 #6).
- [ ] **Confidence and review.** Persist `extraction_confidence`; set `needs_review` for
      low-confidence rows, unknown categories and fuzzy near-matches. That flag is what 3.4
      reads.
- [ ] **Re-import is reconciliation, not just insertion.** When an import overlaps
      transactions an earlier import already wrote for the same account, a row matching on
      `(account, date, amount)` with a different description must be offerable as an
      **update to the existing row** — not only as "keep both" or "delete one". Expose it
      so 3.4 can act on it; a user who re-imports after we fix a parser should not be
      hand-deleting their old rows.
- [ ] **A merge never overwrites the user.** If the existing row's description or category
      was corrected by the user (it has a `category_correction`, or `needs_review` is
      already cleared), the merge keeps theirs. We improved the parse; they told us what it
      actually was.
- [ ] Extend `GET /statements/{import_id}` to report the outcome: saved, duplicates skipped,
      flagged for review.

## 🎯 Acceptance Criteria

- [ ] Importing the **same statement twice** saves the rows once. The second import reports
      every row as a duplicate and creates no transaction — proven by a test that runs the
      import twice and counts rows.
- [ ] Two overlapping statements (January, then January–February) save the union, not the
      sum, of their rows.
- [ ] A genuine same-day, same-amount repeat purchase at the same merchant **is** saved and
      flagged rather than dropped — the dedup rule must not eat real spending.
- [ ] **Re-importing the same statement after the description changes** (simulate a better
      parse: same account, date and amount, different description) flags every affected row
      as a near-duplicate and offers a merge — it does not write a second set of rows and
      leave the user to delete the first by hand.
- [ ] Merging onto a row the user has already corrected keeps the user's description and
      category, not the re-import's.
- [ ] A change to `normalized_description` ships with a backfill: a test asserts every
      stored `normalized_description` equals what the current function produces for its
      `description` — so the next normalizer change fails CI until its backfill exists.
- [ ] `normalized_description` is deterministic: the same description always normalizes to
      the same string, across processes, with a table-driven test covering reference
      numbers, store numbers, embedded dates and casing.
- [ ] Amounts round-trip exactly as decimal strings; no `float` anywhere in the path.
- [ ] The categorization request body contains **only merchant strings and amounts** — a
      test asserts no date, account id, description tail, balance, email or phone reaches
      the model.
- [ ] A model answer that is not a known slug lands in `other` with `needs_review = true`,
      and creates no category row.
- [ ] Corrections from household A never appear in household B's prompt (covered by a test).
- [ ] `POST /accounts` refuses a duplicate name in the same household with 409, logged via
      `log_conflict`; two households may each have "RBC Chequing".
- [ ] One household can never read or write another's accounts or transactions.
- [ ] Migrations apply, reverse and re-apply cleanly in CI's `database` job; `ruff check`,
      `ruff format --check` and `pytest` pass; CI green.
