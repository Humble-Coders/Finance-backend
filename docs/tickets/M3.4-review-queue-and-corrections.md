# [M3] Review queue and correction learning

## 📖 Story / Why

Extraction is never perfect, and this design has no vision fallback — so every row the
model was unsure about, every unknown category and every suspected duplicate has to reach
a person. That is the review queue.

The second half is what makes it worth the user's time. A correction is not just a fix to
one row: it teaches the categorizer for **that household**, so the same merchant lands
right next month (PRD F3). Never across households — one person's labels are not training
data for anyone else, and that is a promise in Appendix A, not a preference.

## ✅ Scope / What to build

- [ ] **`GET /transactions/review`** — the household's rows with `needs_review = true`,
      newest first, paginated with an opaque cursor. Each row carries why it is here:
      low confidence, unknown category, or suspected duplicate. The reason is what lets the
      client show the right affordance instead of one undifferentiated list.
- [ ] **`PATCH /transactions/{id}`** — correct a row: category, merchant, description,
      amount, date, direction. Clears `needs_review` when the user has answered. Amounts
      through `app/core/money.py`; a correction that changes amount or date **recomputes
      `normalized_description` and re-checks dedup**, because the user may have just made
      this row a duplicate of a real one.
- [ ] **`POST /transactions/{id}/confirm`** and a bulk `POST /transactions/confirm` —
      accept rows as they are. Bulk exists because the common case is twenty correct rows
      and two wrong ones, and making someone tap twenty times to say "yes" is how a review
      queue gets abandoned.
- [ ] **`DELETE /transactions/{id}`** — for a row that is not a real transaction at all
      (a header the parser mistook for a line, a duplicate the user recognises). Hard
      delete; this is the user's own data and they are saying it is wrong.
- [ ] **Record the correction.** A category change writes a `category_correction` with the
      predicted and corrected category and a `merchant_pattern` derived from the row's
      normalized merchant. One rule per merchant pattern per household — correcting the
      same merchant again **updates** the rule rather than stacking contradictory ones.
- [ ] **Apply the rule to what is already there.** After a correction, other unreviewed
      transactions in the same household matching that merchant pattern take the new
      category. Bounded and explicit: only rows still `needs_review`, never rows the user
      already confirmed, and the response says how many moved.
- [ ] **User-defined categories.** `POST /categories` (household-scoped) so a correction
      can point at a category the taxonomy does not have. Slug generated from the name,
      unique per household; it must be impossible to create a system-level category through
      this endpoint.
- [ ] **Mark the import finished.** When no row from a `statement_import` still needs
      review, set `confirmed_at`. That is what "the user confirmed the extracted rows"
      means now that there is no document to delete behind it.

## 🎯 Acceptance Criteria

- [ ] The review list returns only this household's rows, only those needing review, and
      each carries its reason; paging with the cursor never skips or repeats a row.
- [ ] Correcting a category writes exactly one `category_correction`, and correcting the
      same merchant again updates that rule rather than adding a second.
- [ ] After a correction, other **unreviewed** rows for the same merchant take the new
      category, and rows the user already confirmed are untouched — proven by a test with
      one of each.
- [ ] A correction that changes an amount or a date re-runs dedup: if it now collides with
      an existing transaction, the response says so instead of writing a duplicate.
- [ ] Bulk confirm accepts a list, is idempotent, and a row belonging to another household
      anywhere in that list fails the whole request — partial application across households
      is not an acceptable outcome.
- [ ] `POST /categories` cannot create a system category (`household_id` NULL) however the
      request is shaped, and cannot duplicate a slug within the household (409, logged).
- [ ] An import whose last review is resolved gets `confirmed_at`; one with a row still
      outstanding does not.
- [ ] Corrections never cross households: a test asserts household A's corrections are
      invisible to B's reads and prompts.
- [ ] `ruff check`, `ruff format --check` and `pytest` pass; migrations apply, reverse and
      re-apply cleanly; CI green.
