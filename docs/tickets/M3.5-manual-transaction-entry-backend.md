# [M3] Record a transaction the user typed in

## 📖 Story / Why

F2 has always said people can add transactions by hand. Since 2026-09-21 it carries more
weight than that: with the LLM-vision fallback deliberately removed, **typing it in is the
only way in when a document cannot be read.** A blurred photo, an unusual layout, a bank
we have not tuned for — without this, those people have no route into the product at all.

It is also the honest baseline. Someone who wants to try FinAI with three transactions
before trusting it with a statement should be able to.

## 🧭 Context

- Repo: `Finance-backend`. No brief — drafted from `docs/ROADMAP.md` and the PRD.
- **Depends on 3.3** for accounts, `normalized_description` and the category taxonomy.
- `transaction.source` already has `manual` (`app/models/enums.py`) — the table was built
  source-agnostic for exactly this.
- A manual transaction has **no `statement_import_id`**. Everything else about it is the
  same row the import path writes, which is the point of a source-agnostic table.
- Money conversion is `app/core/money.py` only.

## 🔑 Access & prerequisites

- Write access to `Humble-Coders/Finance-backend`; `DATABASE_URL` from the manager.

## ✅ Scope / What to build

- [ ] **`POST /transactions`** — `account_id`, `occurred_on`, `amount` (decimal string),
      `direction`, `description`, optional `category_id`. Sets
      `source = TransactionSource.manual`, computes `normalized_description` with the same
      function 3.3 uses, and returns the created row.
- [ ] **Categorize when the user did not.** With no `category_id`, run the same
      `(merchant, amount)` categorization 3.3 uses, including the household's corrections.
      A user who picked a category is never overridden.
- [ ] **Dedup applies here too.** A manual entry that collides with an existing transaction
      returns **409** naming the row it matches, logged via `log_conflict`. Someone typing
      in a coffee they already imported should be told, not quietly given two.
- [ ] **`PUT /transactions/{id}`** for editing a manual row, reusing 3.4's correction path
      where it already does this — do not write a second editing endpoint if 3.4's
      `PATCH` covers it. Say which you chose and why in the handoff.
- [ ] Validation → 422 naming the field: amount valid for the currency and non-negative
      (direction carries the sign), date not in the future beyond a day's tolerance,
      description 1–512 characters.

## 🎯 Acceptance Criteria

- [ ] A manual transaction is saved with `source = manual`, no `statement_import_id`, and a
      `normalized_description` identical to what the import path would compute for the same
      description.
- [ ] Amounts round-trip exactly as decimal strings; no `float` in the path.
- [ ] A manual entry duplicating an existing transaction returns 409 naming the match, and
      writes nothing.
- [ ] With no category given, the row is categorized and the household's existing
      corrections apply; with one given, it is kept exactly.
- [ ] A future date, a negative amount, a missing account and an account belonging to
      another household are each refused with the right status and the field named.
- [ ] `ruff check`, `ruff format --check` and `pytest` pass; CI green.

## 🚫 Out of scope

- The form itself — the mobile ticket in `FinAI-Mobile-2026`.
- Recurring or split transactions — not in v1.
- Bulk manual import (CSV) — not in v1.

## 🔗 Dependencies

- **Needs 3.3** (accounts, normalization, taxonomy). Overlaps 3.4 on editing — read it
  first and reuse rather than duplicate.
- Paired with the mobile ticket of the same number.
